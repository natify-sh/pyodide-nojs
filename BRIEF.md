# Read this first

The briefing for anyone (person or agent) who starts work on this repository. Everything else is reference material: read it when a task needs it. The rules of work are in [CLAUDE.md](CLAUDE.md).

## What this project is, in one paragraph

**pyodide-nojs runs Pyodide's CPython, and its wheels, on Wasmtime (through wasmtime-py) with no JavaScript.** Pyodide's `pyodide.asm.wasm` imports 263 functions from `env` (264 in the package's wasm, after the `setsockopt` patch below): Emscripten's JavaScript glue. Here the glue is **wasm**
(`wasm/adapter.c`, built with wasi-sdk 34's clang, after the shape of Wasmtime's preview1 adapter: no data section, no stack of its own): system calls over WASI, the dynamic loader (`dlopen` of a wheel), libffi calls, sockets,
time, the trampoline. The Python host (`src/pyodide_nojs/_host.py`, class `Pyodide`) gives what a wasm module cannot do: wasmtime's WASI, the loader operations, libffi's calls and callbacks, the host's time zone, the host's sockets, `statvfs` and terminal: 38 operations in all, each with the reason it is the host's, in `docs/HOST_CONTRACT.md`. Pyodide is **not rebuilt**: its wasm is the npm
package's, with the legacy wasm exceptions converted once to `exnref`. The package is an **alpha** and meant to be a ready solution for anything Pyodide runs without the browser's JavaScript, not for numpy only.

## What it is NOT

* **Not Pyodide's JavaScript API.** `js`, `pyodide.ffi`, `JsProxy`/`PyProxy`, `loadPackage` from JS need the bridge; the 169 `env` imports that are the bridge (158) and hooks without meaning here (11) are zero/null stubs, listed one by one in `docs/IMPORT_AUDIT.md`. Tests that need them are N/A, not failures.
* **Not a rebuild of Pyodide or of Emscripten.** The one change to Pyodide's binary is made at build time (`tools/patch_main.mjs`): libc's `setsockopt`, which Emscripten compiles to `return 0` without calling the syscall, becomes a call of an import the adapter answers; each such stub needs its own patch. One Pyodide build is supported (`PYODIDE_VERSION` 315.0.0-alpha.2, ABI `pyemscripten_2026_5_wasm32`); the adapter answers that build's imports.
* **Not a sandbox against the host's kernel.** The guest's `/` is a temporary folder; the network is off by default and `--inherit-network` (or `--tcp`, `--udp`, `--dns`, `--http`; the owner, 2026-11-16) hands the host's sockets, name lookup and fetch over; `mounts` hand host folders over.
* **Not a Node or a Binaryen user at run time.** Node and npm's Binaryen are **build** tools (`tools/*.sh`, CI). The run time needs wasmtime-py and the wasm files in the wheel.
* **Not a Component Model component (for now).** Emscripten's ABI does not fit it: a wheel's `.so` imports the main module's memory, table, stack pointer, exception tag and `GOT.*` globals, which cannot cross component instances; the `env`
  imports are Emscripten's JavaScript glue, not WIT; and `dlopen` needs a new core module at run time, which a component cannot create. So Fastly Compute, Spin and wasmCloud, which run components, are not targets. Stock CPython for WASI
  (e.g. `componentize-py`) cannot load binary wheels at all (WASI has no `dlopen`); **loading Emscripten wheels at run time, by a host we control, is what this project does** and why it exists. Details and the open question: `docs/NOTES-FUSEDWASI-AND-TESTSUITE.md`, section 3.
* **Not wasmhost.** [wasmhost](https://github.com/natify-sh/py-wasmhost) is the sibling (the WebAssembly API on many engines); this package came out of its experiments (`docs/EXPERIMENT.md`) but depends on nothing of it.

## The architecture in five lines

```
data/ (in the wheel):  pyodide.asm.wasm (exnref) + adapter.wasm  -> "dynamic": linked at run time (shim from the import list, trampoline, fixup)
                       pyodide_fused.wasm (tools/fuse.py, wasm-merge) -> "fused": one core module, only instantiated
                       python_stdlib.zip, wasm-opt.wasm (Binaryen 132 as wasm32-wasip1: converts a wheel's legacy exceptions at dlopen, in-process)
                       pyodide-lock.json, tls/ (the real _ssl + ssl.py, tools/build_ssl.sh), py/ (micropip, packaging)
_host.py (Pyodide)  WASI = wasmtime's own; 38 host operations (docs/HOST_CONTRACT.md): loader.* (16: the loader, libffi, time zone, CPU clocks), net.* (19: sockets, DNS; _net.py Net also the host's fetch), fs.* (3: statvfs, ioctl and read for the terminal: _tty.py); run() calls `pyodide_nojs_run.run`/`run_async` through the C API (`PyImport_ImportModule`, `PyObject_CallOneArg`)
_engine.py          the engine, the machine-code cache (~/.cache/pyodide-nojs), wasm-opt.wasm run in-process
tests/              offline + network + Pyodide's official CPython suite, each on BOTH builds;  CI: build.yml -> tests.yml / publish.yml
```

## Where it is, and what is next

* **Done (as of 2026-11-16):** the package on a branch that is not merged yet: both builds, CLI, API, wheel (13 MB, measured 2026-11-16), tests, CI written. The state of the official suite and of CI is in `BACKLOG.md` (section 3, "Order of work") and the CI runs, not here. `Pyodide(preload=)` starts from a cached memory snapshot (`tests/test_snapshot.py`; the REPL's start to the first prompt 0.7 s -> 0.3 s with asyncio preloaded); one snapshot per packaging is kept, so alternating preloads (e.g. the REPL with and without `--allow-top-level-await`) rewrites it each time.
* **Next:** `BACKLOG.md`, "Order of work" (the audit of the documents, then the alpha line: green CI on all three systems, the wheel installed and run in a clean environment); later, from [docs/NOTES-FUSEDWASI-AND-TESTSUITE.md](docs/NOTES-FUSEDWASI-AND-TESTSUITE.md): the rest of the official suite (`test_python_socket.py`, the package tests of numpy/cffi/micropip/test-cpp-exceptions) and WASI 0.2 over fusedwasi, replacing the `net` operations.
* **Decided (owner, 2026-11-10; confirmed later, BACKLOG D1): the callback of `emscripten_dlopen` stays as it is.** It is a pending call of the interpreter (`Py_AddPendingCall`): it runs right after the call returns, before the next statement; Pyodide runs it from its JavaScript event loop, so there it comes after the current synchronous code. Until something needs the other: if a program depends on the order (state set right after the call must precede the callback), switch to option C: queue the job and run it where Pyodide's event loop would turn, in `time.sleep`, `poll`/`select` and at the end of `run()` (a hook on the host's wait operations; how `time.sleep` reaches the host in this build is not measured yet). The other options (run only at the end of `run()`, or synchronously as before) and the probes are in the audit entry of `_emscripten_dlopen_js` (docs/IMPORT_AUDIT.md).
* **The official suite: 0 failed on both packagings in CI (2026-11-16); no list of known failures (owner, 2026-11-10).** What cannot be fixed in this architecture is recorded with its concrete reason, per test, in `tests/suite_overrides.yaml` (an `xfail` only for a module that cannot run at all) (what WASI, wasmtime or the missing JavaScript lacks): the skipped and xfailed results have these reasons. A failure that appears is read from the junit file of the CI suite jobs (artifacts `suite-<flavor>`), not by running the suite for hours locally.
* **Sockets follow the host's kernel (owner, 2026-11-11).** The guest's sockets are real sockets of the host (`net.*` operations over Python's `socket`); Pyodide on Node has none, so there is no Pyodide behaviour to equal: the reference is POSIX/Linux, and on macOS and Windows what a native Python does on that OS. What the host normalises to Linux's answer: on/off options of `getsockopt` read 0/1 (BSD returns the option's bit), `SO_ACCEPTCONN` comes from the host's own record of `listen()`, a refused non-blocking `connect` reports POLLERR with the error kept for one `getsockopt(SO_ERROR)`, a datagram `send` without a peer is EDESTADDRREQ. What it does NOT normalise, on purpose: a kernel's own answer, e.g. poll reports POLLHUP at once for a peer that only closed on macOS and not on Linux, `shutdown` on a closed peer is ENOTCONN on BSD, Windows' `select()` has no POLLHUP (the host adds it after `shutdown(SHUT_RDWR)` only). A program that needs the same on every host must not rely on these; the tests say which OS answers what (`tests/test_sockets.py`).
* **Other Pyodide versions (owner, 2026-11-10): Python 3.14 is not supported for now; noted.** Tried: Pyodide 314.0.7 (CPython 3.14.2, npm) through `--asm-wasm`/`--stdlib` on dynamic: the four start-up warnings are right (CPython version, one unknown import `__syscall_pipe`, no `setsockopt` patch, a 3.14 stdlib zip while the host lays out 3.15) and the run traps at boot with `indirect call type mismatch`. The imports of the two builds agree except: `_gmtime_js` and `_localtime_js` are `(i64, i32) -> void` in 314 and `(i64, i32) -> i32` in 315 (the likely cause of the trap, not proven), 314 has `__syscall_pipe` that 315 lacks, 315 has ten that 314 lacks (`epoll_*`, `pipe2`, `getegid32`/`geteuid32`/`getgid32`, `linkat`, `poll_nonblocking`, `shutdown`); `PYVER` is also fixed in the host. The owner's direction for later: a signature mismatch between a main-module import and the adapter's export must not trap at the call: bind a stub instead and say so with a warning at start (name, both signatures), so another version runs as far as it can; the stub's result must be honest by type (`-ENOSYS` for `__syscall_*`, 0/null otherwise) and the warning must name every stubbed function. Nothing of it is built; the warning for a name the adapter does not know exists, one for a different signature does not.
* **Start state (2026-11-11):** the guest starts as Pyodide does: the host calls the main module's own `__main_argc_argv(1, ["./this.program"])` (Pyodide's `main()`: PyConfig with home `/`, `stdlib_dir` the zip, no bytecode, `Py_InitializeFromConfig`) from `/home/pyodide`. So `sys.executable`, `sys.orig_argv`, `sys.argv`, `sys.path`, `sys._stdlib_dir`, the frozen modules' `__file__` and the cwd are Pyodide's own (`tests/test_review_fixes.py::test_startup_state_is_pyodides`, also after a snapshot restore). Deliberate differences: `PYTHONINSPECT=1` of Pyodide's JavaScript is mirrored (`sys.flags.inspect` is 1, as in Pyodide); `sys.executable` is the web's `/home/pyodide/this.program` (on Node the real one is a script path); fewer modules are loaded at start (84 against 197, `len(sys.modules)` at the start of a run, measured 2026-11-16 on both packagings with `Pyodide(flavor).run('import sys; print(len(sys.modules))')`; `tests/boot_modules.py`; the `pyodide` Python package and its JavaScript bridge are not here); `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` are set; `sys.path` has `''` first as Pyodide's JavaScript puts it.
* **Standards we follow:** core WebAssembly 3.0 (exnref, GC, function references), the `dylink.0` convention (LLVM/Emscripten tool-conventions) for side modules, PEP 783 for the wheel tag (`pyemscripten_YYYY_N_wasm32`), WASI 0.1 now and 0.2/0.3 for sockets, HTTP and files next (replacing our `net` operations). The `loader.*` interface (16 operations today, with `net.*` and `fs.*` 38 host operations in all: `docs/HOST_CONTRACT.md`) is our own extension and the contract between the adapter and a host.
* **Waiting for the owner:** a pull request (the assistant does not open one); `BACKLOG.md` section 1 for the other open questions (the license/size policy of Pyodide artifacts is decided for the alpha: they stay in the wheel); `CLAUDE.md` rules that were taken from wasmhost and are not yet confirmed for this project (below).

## Direction: one adapter, two ways to run it (decided 2026-11-10; the second is a plan, nothing of it is built)

1. **Host mode (what this package does).** A Python host on wasmtime-py: `dlopen` of a wheel at run time through the `loader.*` operations, sockets through `net` (or WASI 0.2 sockets). Full: any Emscripten wheel, `micropip`, TLS in the guest. Everything below "Where it is" is about this mode.
2. **Bundle mode (for hosts that run components: Fastly, Spin, wasmCloud).** A CLI that bundles Pyodide, the chosen wheels and the adapter with **`dlopen` answered inside the module** (a registry of what was linked at build time) into **one component**. A component can not create a module at run time and does not give the host its memory and table, so the set of wheels is fixed when it is bundled. What exists: a component with TCP and DNS over `wasi:sockets` on a separate branch that is not merged (not in this tree); what is missing: the bundling of wheels (bases of memory and table, `GOT`, `__wasm_apply_data_relocs`, the registry), and then `_ssl`, `libssl`, `libcrypto` for HTTPS without `wasi:http`. Decided not to do: `wasi:http` as a host fetch, fusedwasi as a way to host components.
   * Tooling: `wasm-tools-package` (natify-sh, `pip install wasm-tools-package`, Python 3.11+) as an optional dependency of the bundler. **To try first:** `wasm-tools component link --dl-openable NAME=lib.so` with `--use-built-in-libdl` implements exactly this (linking by the `dylink.0` convention, `dlopen` of what was bundled); whether it accepts Pyodide's `MAIN_MODULE` as the base, and Emscripten `.so` files, is unknown. Binaryen's `wasm-merge` is the fallback (it is what `tools/fuse.py` uses).
   * Order: finish the failures of the official suite in host mode; bundle one small module (`_testbuffer.so`) to prove the mechanics; then numpy and `_ssl`; then the CLI.

Pyodide's CPython suite: now (CI, 2026-11-16, fused and dynamic alike) 823 results: 607 passed, 186 skipped, 30 xfailed, 0 failed; the first run (2026-11-10) was 500 passed, 103 failed, 185 skipped, 31 xfail (module level: one failing test fails a module). Not compared with Pyodide on Node. ## Hard rules (short form; the full list is in CLAUDE.md)

* The package has **no run-time Python dependency**; wasmtime-py is the `[wasmtime]` extra (and a dev dependency). Python 3.10+.
* **Node is a build tool only**; one toolchain, **wasi-sdk 34's clang**, builds every wasm we build, except the guest's `_ssl` (pyodide-build, Emscripten 6.0.5: `tools/build_ssl.sh`).
* **Both packagings** (fused, dynamic) are tested everywhere a test runs, **including Pyodide's official suite**.
* **The guest is isolated** from the host's environment, files and (by default) network (D13), with two named exceptions: `--inherit-env` hands over ALL the host's variables, secrets included (and then no snapshot is written), and the CA bundle for TLS is read from the host (`SSL_CERT_FILE`, Python's, the system's: a file with a private key in it would put the key into the guest's `/etc/ssl/cert.pem`; the CA bundle is still open under D13).
* Measure, do not guess: a claim about what runs has a command or a CI run behind it; say plainly what was not run (a network check in a sandbox, Windows, macOS).
